# GEAK Kernel Optimization — Optional Extension

## Relationship to Main Skill

This skill is an **optional extension** of `workload-optimization/SKILL.md`. It adds a kernel-level optimization path using GEAK MCP, complementing the config overrides and code patches in the main skill.

**Main skill** = config/code-level: config overrides (`moe_permute_fusion`, etc.), code patches (caching, fused ops), attention backend swaps
**This skill** = kernel-level: rewrites the actual GPU kernel source (Triton or HIP) for a specific hot kernel

### When to Invoke This Skill

During the main optimization loop (after TraceLens profiling in Step 3, or after any re-profile), check if GEAK can help:

| Kernel type in profile | GEAK applicable? | Why |
|------------------------|-------------------|-----|
| `Cijk_*` (hipBLASLt GEMM) | **No** | Vendor BLAS; hand-tuned MFMA; GEAK can't beat it |
| `aiter::fmha_v3_*` | **No** | Vendor attention; already optimized for gfx950 |
| `triton_*` / `triton::` | **Yes** | Triton kernels have Python source; GEAK can rewrite |
| `vectorized_elementwise_kernel` | **Maybe** | If unfused, better to torch.compile first; if still hot, extract and GEAK |
| Custom HIP kernels (`__global__`) | **Yes** | Primary GEAK target |
| Custom fused ops (RMSNorm, rotary, etc.) | **Yes** | If source is available |
| `FmhaBwdDQDKDVKernel` (CK legacy) | **No** | Composable Kernel library; switch backend instead |

**Decision rule:** If a kernel is in the top-5 by GPU time, has modifiable source code, and is NOT vendor BLAS, it's a GEAK candidate.

## Prerequisites

- GEAK MCP configured in `.cursor/mcp.json` (see `kernel-regression-analysis/mcp-config.md`)
- Environment variables in `.env` at repo root:
  ```
  LITELLM_API_KEY=sk-...          # LLM gateway key for GEAK's internal LLM
  PRIMUS_SAFE_API_TOKEN=ak-...    # Auth token for GEAK endpoint
  ```
- A TraceLens analysis already completed (trace file + kernel profile from main skill)
- The source code for the candidate kernel (Triton `.py`, HIP `.hip`/`.cu`, or extracted from Python)

## Phase 1: Identify GEAK Candidates from TraceLens Output

After TraceLens runs in the main skill, you have a kernel profile. Scan it:

```python
# Pseudocode for the agent's reasoning
geak_candidates = []
for kernel in top_20_kernels:
    if kernel.name.startswith("Cijk_"):
        continue  # vendor BLAS, skip
    if "aiter::" in kernel.name:
        continue  # vendor attention, skip
    if "FmhaBwd" in kernel.name:
        continue  # CK library, switch backend instead
    if kernel.gpu_time_pct > 3.0:  # >3% of total GPU time
        geak_candidates.append(kernel)
```

For each candidate, determine:
1. **Source location**: Where is the kernel defined?
2. **Source type**: Triton Python, HIP C++, or inline CUDA?
3. **Extraction method**: How to get the source text?

### Finding Kernel Source

**Triton kernels** (name contains `triton`):
```bash
# Triton kernels are defined in Python with @triton.jit
# Search the workload code and its dependencies:
rg "@triton.jit" /path/to/workload/
rg "def <kernel_name>" /path/to/workload/

# Also check installed packages:
python3 -c "import <package>; print(<package>.__file__)"
rg "@triton.jit" $(python3 -c "import <package>; import os; print(os.path.dirname(<package>.__file__))")
```

**Custom HIP/CUDA kernels** (name matches a `__global__` function):
```bash
# Search for the kernel name in .hip, .cu, .cuh files
rg "void <kernel_name>" /path/to/source/ --glob "*.{hip,cu,cuh}"
```

**aiter internal kernels** (if you need to check what's inside):
```bash
# aiter kernels are in compiled .so files — source not directly available
# But the Python dispatch logic is in:
python3 -c "import aiter; print(aiter.__file__)"
# Check aiter/ops/ for the Python wrapper that calls the kernel
```

**torch.compile generated kernels** (name like `triton_poi_*`, `triton_red_*`):
```bash
# These are auto-generated by Inductor. Source is in the Triton cache:
ls /tmp/torchinductor_*/*/triton/*.py
# Extract the relevant .py file for the hot kernel
```

## Phase 2: Extract Kernel Source

### PREFERRED: Auto-Extract from torch.compile (Inductor)

**This is the recommended approach** when the training stack supports `torch.compile`. Instead of hand-writing Triton kernels, use `torch.compile` to generate them automatically. One run gives you BOTH:
1. Profiler trace (for Jarvis/TraceLens)
2. Inductor-generated Triton kernels (for GEAK)

If an `inductor_extract.py` utility is available (e.g., in `.cursor/agents/executors/`), use it:

```python
import sys; sys.path.insert(0, ".cursor/agents/executors")
from inductor_extract import run_combined_pipeline
results = run_combined_pipeline("<model_script_or_module>")
# results contains:
#   trace_path       → send to Jarvis/TraceLens
#   inductor_files   → Triton source files in Inductor cache
#   matched_kernels  → kernels matched to profile (sorted by GPU time)
#   all_kernels      → all extracted kernel functions
```

Or from the command line:
```bash
python3 .cursor/agents/executors/inductor_extract.py <model_script_or_module>
```

**Note:** For distributed training (e.g., Primus/Megatron with `torchrun`), `torch.compile` extraction is harder to integrate — graph breaks are common with distributed ops. In that case, use manual extraction (below) with kernels found via the profiling trace from Step 3 of the main skill.

**How it works:**
1. Sets `TORCHINDUCTOR_CACHE_DIR=/tmp/inductor_geak_cache` — known location for extraction
2. Loads workload and wraps model with `torch.compile(mode='default')`
3. Warmup triggers Inductor compilation → generates Triton `.py` files in cache
4. Benchmarks the compiled model
5. Profiles (model is already compiled, no recompilation during profiling)
6. Scans Inductor cache for files containing `@triton.jit`
7. Parses kernel functions and matches to profile hotspots
8. Writes GEAK-ready kernel files

**Example Inductor-generated kernel** (RMSNorm fwd — auto-extracted, no hand-writing):
```python
# From /tmp/inductor_geak_cache/sm/csm44...py
@triton_heuristics.reduction(
    size_hints={'x': 8192, 'r0_': 4096},
    reduction_hint=ReductionHint.INNER,
    triton_meta={'signature': {...}, 'device': DeviceProperties(type='hip', cc='gfx950', ...)},
)
@triton.jit
def triton_red_fused__to_copy_add_mean_mul_pow_rsqrt_0(in_out_ptr0, in_ptr0, in_ptr1, out_ptr0, ...):
    # Inductor auto-generated: fused cast + pow + mean + rsqrt + mul = RMSNorm
    xnumel = 8192; r0_numel = 2880
    # ... auto-generated kernel body with proper tiling and vectorization ...
```

**Key advantage:** These kernels already include:
- Correct shapes hardcoded (`xnumel = 8192`, `r0_numel = 2880`)
- AMD gfx950 device properties
- Inductor's heuristic-chosen block sizes and num_warps
- Proper eviction policies (`evict_last`, `evict_first`)
- `tl.debug_barrier()` for synchronization

```bash

  -H "$GEAK_AUTH" \
  -d '{
    "jsonrpc":"2.0","id":1,"method":"tools/call",
    "params":{
      "name":"geak_set_model_config",
      "arguments":{
        "model_class":"litellm",
        "model_name":"openai/claude-opus-4-6",

          "max_tokens":8192,
          "temperature":0.0
        }
      }
    }
  }'
```

### 3c. Create task with kernel source + context

The key to good GEAK results is providing **rich context** in the `prompt` argument.

**CRITICAL API notes (learned from testing):**
- The argument is `prompt`, NOT `instructions` (the latter causes an error)
- `input_type` is **required** — use `"file"` when providing files
- `step_limit` controls agent iterations (default 20; use 5 for quick tests)
- `gpu_count` defaults to 1

Use Python to build the JSON payload (avoids bash escaping headaches):

```bash
curl -sk -X POST "$GEAK_URL" \
  -H "Content-Type: application/json" \
  -H "$GEAK_AUTH" \
  -d "$(python3 -c "
import json
with open('kernel_candidate.py') as f:
    src = f.read()
payload = {
    'jsonrpc': '2.0', 'id': 2, 'method': 'tools/call',
    'params': {
        'name': 'geak_create_task',
        'arguments': {
            'input_type': 'file',
            'files': [{'filename': 'kernel_candidate.py', 'content': src}],
            'prompt': '''Optimize this GPU kernel for AMD MI355X (gfx950, CDNA4).

Hardware: 304 CUs, 256 VGPR/CU, HBM3e ~8 TB/s, MFMA instructions.
Input shapes: [describe exact shapes from profile]
Currently achieving Y TFLOPS (Z% of peak).
Called N times per training iteration, X% of total GPU time.

Goals: (1) maximize throughput, (2) minimize register pressure,
(3) vectorized loads for HBM3e, (4) optimal block sizes for gfx950.
Return optimized kernel with same function signature.
Write output to the output directory.''',
            'step_limit': 5,
            'gpu_count': 1
        }
    }
}
print(json.dumps(payload))
")"
```

**Tip:** If the kernel imports from other modules, include those as additional files in the `files` array. GEAK works best with self-contained code.

### 3d. Submit and poll

```bash
# Extract task_id from create response
TASK_ID="<from create response>"

# Submit
curl -sk -X POST "$GEAK_URL" \
  -H "Content-Type: application/json" \
  -H "$GEAK_AUTH" \
  -d '{
    "jsonrpc":"2.0","id":3,"method":"tools/call",
    "params":{"name":"geak_submit_task","arguments":{"task_id":"'"$TASK_ID"'"}}
  }'

# Poll until complete (typically 10-30 minutes — GPU pod scheduling + agent steps)
for i in $(seq 1 30); do
  sleep 30
  STATUS=$(curl -sk -X POST "$GEAK_URL" \
    -H "Content-Type: application/json" \
    -H "$GEAK_AUTH" \
    -d '{
      "jsonrpc":"2.0","id":4,"method":"tools/call",
      "params":{"name":"geak_get_task","arguments":{"task_id":"'"$TASK_ID"'"}}
    }')
  echo "Poll $i: $STATUS"
  if echo "$STATUS" | grep -q '"completed"'; then
    break
  fi
done

# Get outputs
curl -sk -X POST "$GEAK_URL" \
  -H "Content-Type: application/json" \
  -H "$GEAK_AUTH" \
  -d '{
    "jsonrpc":"2.0","id":5,"method":"tools/call",
    "params":{"name":"geak_get_outputs","arguments":{"task_id":"'"$TASK_ID"'"}}
  }'
```

### 3e. Download optimized kernel

```bash
# For each output file from geak_get_outputs:
curl -sk -X POST "$GEAK_URL" \
  -H "Content-Type: application/json" \
  -H "$GEAK_AUTH" \
  -d '{
    "jsonrpc":"2.0","id":6,"method":"tools/call",
    "params":{"name":"geak_download_file","arguments":{
      "task_id":"'"$TASK_ID"'",
      "filename":"<output_filename>"
    }}
  }'
```

## Phase 4: Reintroduce GEAK-Optimized Kernels

There are two paths depending on how the kernel was extracted.

### Path A: Inductor Auto-Extracted Kernels (PREFERRED)

If you used `inductor_extract.py` to auto-extract kernels from `torch.compile`, you can **patch the optimized kernel directly back into the Inductor cache**. This is the cleanest approach — the model continues to use `torch.compile` and the patched kernel is picked up automatically.

**Step-by-step:**

```python
import sys; sys.path.insert(0, ".cursor/agents/executors")
from inductor_extract import patch_kernel_in_file

# 1. Read GEAK's optimized kernel source
with open("geak_output_kernel.py") as f:
    optimized_source = f.read()

# 2. Patch it into the Inductor cache file
#    (keeps same function name, replaces the kernel body)
patch_kernel_in_file(
    inductor_file="/tmp/inductor_geak_cache/sm/csm44...py",
    original_kernel_name="triton_red_fused__to_copy_add_mean_mul_pow_rsqrt_0",
    optimized_source=optimized_source,
)
# This also backs up the original and clears Triton binary cache
```

**How to rebenchmark after patching:**

```bash
# Clear Triton binary cache and FxGraph metadata (force recompile)
rm -rf /tmp/inductor_geak_cache/triton/*
rm -f /tmp/inductor_geak_cache/**/*.json

# Re-run training with all kept overrides (Inductor reloads patched .py, recompiles Triton)
TORCHINDUCTOR_CACHE_DIR=/tmp/inductor_geak_cache \
torchrun --nproc_per_node=<NUM_GPUS> --master_port=<PORT> \
  -m primus.cli.main train pretrain \
  --config <CONFIG_YAML> \
  <all_kept_overrides> \
  profile=false use_pytorch_profiler=false \
  2>&1 | tee /tmp/attempt_geak.log
```

**Important:** Must run in a fresh process. The Inductor cache is loaded at import time; patched files need a new process to take effect.

**Verified flow** (tested on GPT-OSS 20B):
1. Original compiled: 191.91 ms/iter
2. Patched kernel (num_stages 2→3): 191.64 ms/iter
3. End-to-end impact correctly reflected

**Caveats:**
- Must use `torch.compile(mode='default')`, NOT `mode='reduce-overhead'`
  (reduce-overhead uses CUDA graphs that capture kernel launches; patched kernels won't be picked up)
- Clearing `.json` metadata files forces Inductor to reload the `.py` source files
- Clearing the Triton binary cache (`/triton/`) forces kernel recompilation
- Always run the patched benchmark in a **separate Python process**
- If GEAK changed the function signature (args, constexprs), it won't work — signature must match

### Path B: Manual Triton Kernel Replacement (primary for distributed training)

If you extracted kernel source manually from the training stack (no torch.compile), patch the optimized kernel directly into the source file where the original is defined:

```python
# Edit the source file in the training stack (e.g., /workspace/Primus/primus/...):

# Option A: Replace the kernel body in-place
@triton.jit
def _rms_norm_fwd_kernel_optimized(X, W, Y, stride, N, eps,
                                     BLOCK_SIZE: tl.constexpr):
    # ... GEAK's optimized kernel body ...

# Option B: Import from saved file and swap the call site
from geak_optimized_kernel import optimized_kernel_fn
```

Then re-run training with `torchrun` as a normal optimization attempt (see Phase 5).

### Path C: HIP Kernels

```python

```

## Knowledge Base: GEAK-Specific Lessons

### GEAK Can't Beat Vendor BLAS
hipBLASLt GEMMs (`Cijk_*` kernels) use hand-tuned MFMA tile schedules. GEAK generates scalar or basic vectorized HIP code. Never submit GEMM kernels to GEAK — it will produce something 10-100x slower.

### GEAK and Triton Kernels — Mixed Results
GEAK's LLM backend understands Triton syntax and can suggest structural changes (2D grids, fast sigmoid, autotuning configs). However, **GEAK's tuning suggestions may actually regress on AMD CDNA4 (gfx950)**. Tested results:
- **SiLU*mul**: GEAK suggested 2D grid with BLOCK_N=256, 4 warps → **2.2x slower** (too many small thread blocks)
- **RMSNorm**: GEAK suggested BLOCK_N=4096, 16 warps, single-pass → **1.6x slower** (too many warps, register pressure)

GEAK is better suited for **HIP/C++ kernel optimization** where it can apply shared memory tiling, MFMA instructions, and double buffering — patterns that are harder to get wrong than Triton block-size tuning.

### Provide Rich Context to GEAK
The quality of GEAK's output is directly proportional to the context you provide:
- **Always include**: hardware target (gfx950), dtype (bf16), input shapes, occupancy target
- **Include if available**: current TFLOPS and memory bandwidth utilization (from TraceLens)
- **Include if available**: the calling code (how the kernel is launched, grid dimensions)

### GEAK Output May Not Compile
GEAK generates code via an LLM — it may have syntax errors or use unsupported intrinsics. Always:
1. Try to compile/import first before benchmarking
2. If it fails, fix obvious issues (missing imports, wrong types)
3. If unfixable, log as `crash` and move on

### GEAK Output May Be Functionally Wrong
Always verify correctness before benchmarking performance:
```python
# Compare outputs
orig_out = original_kernel(test_input)
geak_out = geak_kernel(test_input)
assert torch.allclose(orig_out, geak_out, atol=1e-2, rtol=1e-2), \
    f"GEAK kernel produces different results! max diff: {(orig_out - geak_out).abs().max()}"
```
Use relaxed tolerances (atol=1e-2) for bf16 kernels.

### One Kernel at a Time
Submit one kernel per GEAK task. Multi-kernel tasks confuse the LLM and produce worse results. If you have 3 candidates, create 3 separate tasks.

### GEAK Latency
Expect **10-30 minutes** per task. The breakdown:
- Pod scheduling on K8s: 2-15+ min (depends on cluster load and GPU availability)
- Docker image pull: 1-5 min (the ROCm PyTorch image is ~15 GB)
- Agent execution: 3-10 min (depends on step_limit and LLM response time)
Poll every 30 seconds. The `updated_at` timestamp stays frozen until the pod actually starts running; once it changes, the agent has started. If stuck for >30 min with no update, the cluster may be overloaded — cancel and retry later.

### torch.compile + GEAK Interaction
If the workload uses `torch.compile` (rare for distributed Primus/Megatron training due to graph breaks, but possible for submodules), Inductor may already be generating optimized Triton kernels for the ops you want to GEAK. In this case:
1. Profile **with** torch.compile active to see the actual Inductor-generated kernels
2. Extract those generated Triton kernels from `/tmp/torchinductor_*/`
3. Submit the Inductor-generated kernel to GEAK (not the original Python)
4. If GEAK improves it, you'll need to **disable** torch.compile for that submodule and use the GEAK kernel directly

For most distributed training workloads, you'll use manual extraction (Phase 2) instead.

### When GEAK Is Not Worth It
- Kernel is <2% of total GPU time (even 50% speedup = <1% end-to-end)
- Kernel is a single simple op (element-wise add, copy) — already bandwidth-bound
- Kernel is from a vendor library (aiter, hipBLASLt, CK) — switch backend instead
- The workload is GEMM-dominated (>60% GEMM) — code-level optimizations matter more

### GEAK Authentication
- Requires `PRIMUS_SAFE_API_TOKEN` (not `LITELLM_API_KEY`) for the Bearer token
- `LITELLM_API_KEY` is used internally by GEAK to call its LLM backend
- Both must be set before submitting tasks

### GEAK Pod Scheduling — Use `control-plane-dev` Space
GEAK MCP submits workloads to `control-plane-anthropic` by default, which is often resource-constrained. To avoid long queue times, launch workloads directly via the Primus-SaFE API targeting `control-plane-dev`:
```bash
curl -sk -X POST "$PRIMUS_SAFE_API_URL/api/v1/workloads" \
  -H "Authorization: Bearer $PRIMUS_SAFE_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d @payload.json
```
Include `"workspaceId": "control-plane-dev"` in the payload. You must replicate the GEAK entrypoint script (clone GEAK repo, install mini-swe-agent, run `mini` command). See the existing GEAK task entrypoints for reference.

**Critical entrypoint fixes (learned from testing):**
1. Must set `export MSWEA_CONFIGURED="true"` before running `mini` — otherwise it enters interactive setup mode
2. Must `pip install requests prompt_toolkit litellm` before `pip install -e .` — the container may not have network access to PyPI for all deps
3. Do NOT copy input files to output at the end — this overwrites GEAK's modifications. The agent writes directly to the output directory.

### Entrypoint Template for Direct Primus-SaFE Launch
```bash
#!/bin/bash
exec > $OUTPUT_DIR/debug.log 2>&1
set -ex
export MSWEA_CONFIGURED=true
cp /shared_nfs/xiaofei/amd-issuing-ca.crt /usr/local/share/ca-certificates/ && update-ca-certificates || true
cd /tmp && git clone -b feature/xiaofei/geak-online https://github.com/xiaofei-zheng/GEAK.git geak
cd geak/geak_v3
pip install requests prompt_toolkit litellm -q 2>/dev/null || true
pip install -e . || pip install -e . --no-deps || true
# SSL trust for LLM gateway
SITE_DIR=$(python3 -c "import site;print(site.getsitepackages()[0])")
cp /tmp/geak/server/ssl_setup.py "$SITE_DIR/" && echo "import ssl_setup" > "$SITE_DIR/zzz_ssl.pth"
# Run agent
mini -c "$TASK_DIR/config.yaml" -t "$TASK_DIR/prompt.md" --yolo >> "$OUTPUT_DIR/execution.log" 2>&1
```
