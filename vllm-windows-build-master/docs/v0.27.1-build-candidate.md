## Windows changes carried into 0.27.1

- Native MSVC/CUDA builds and Windows runtime/platform detection.
- Windows packaging for vLLM's stable-libtorch modules, FlashAttention 2, and
  both optimized Rust artifacts.
- Windows-safe sampling, shared mmap, binary filesystem I/O, asynchronous KV
  copy, and hybrid block-table fallbacks.
- Opt-in CPU LRU/ARC and CPU-plus-filesystem LRU/ARC prompt-KV tiers.
- Turing, Ampere, Ada, and Blackwell architecture coverage in one CPython 3.13
  wheel.

CUDA 13 generates a few SM120-only CUTLASS entry points whose 128-byte-aligned
by-value parameters cannot be represented by the MSVC x64 ABI. Those specific
FP8 scaled-matrix and NVFP4/MoE specializations are omitted on Windows. SM120
remains enabled for the rest of the wheel; this limitation does not remove
Blackwell support generally.

**Post-release finding (issue #16):** the unmodified wheel can still select an
omitted SM120 FP8 backend and fail at startup. The reporter subsequently
confirmed `unsloth/Qwen3.8-27B-NVFP4` serving on an RTX PRO 5000 Blackwell,
Windows 11 Pro, with compilation and CUDA graphs after applying the
[Marlin setting and Python metadata fix](troubleshooting.md#blackwell-fp8-nvfp4).
That result used a modified installed Python file and the existing wheel's
Marlin kernels; it does not establish native FP4 support. The wheel and patch
hashes above still identify the original release artifacts without that fix.

## Validation evidence

All GPU results below came from the final installed wheel on an RTX 3090. The
local model was
`Qwen3.5-9B-abliterated-GPTQ-4bit` (7.15 GiB checkpoint, AutoGPTQ/Marlin).

### Native and API serving

- Python 3.13.11, vLLM 0.27.1, Torch 2.13.0+cu130, and CUDA 13.0 were reported
  from the installed wheel.
- Every packaged `.pyd` and the Rust tool parser imported successfully.
- After installing the pinned companion wheel, all six Multi-TurboQuant cache
  formats passed direct CUDA write/decode smoke tests.
- The OpenAI-compatible API served three deterministic requests successfully
  with no request errors.
- After fixing the launcher's FastAPI request-annotation scope, the integrated
  `vllm_launcher.py` path returned HTTP 200 for both `/health` and
  `/v1/chat/completions`. The request used 17 prompt and 24 generated tokens
  and completed in 2.918 s; the warm-cache model load took 49.6 s.
- Each request used 984 prompt tokens and generated 96 tokens. Wall times were
  18.787 s, 12.887 s, and 12.872 s.
- Prefix-cache counters recorded 1,056 hits from 2,952 prompt tokens (35.77%).
- At `--gpu-memory-utilization 0.80` and 4,096-token context, vLLM reported
  11.52 GiB available for KV cache, 208,896 KV tokens, and 51.00x maximum
  4,096-token concurrency.
- Model weights used 7.2 GiB. The first cold file-cache load took 168.88 s;
  warm operating-system-cache loads in later validation runs took 7.76-9.77 s.

### Windows KV tiers

The tests cleared the GPU prefix cache between requests and required exact
generated token IDs after restoration.

| Mode | Cold | Restored/restarted | Cached prompt tokens | Result |
|---|---:|---:|---:|---|
| CPU LRU | 3.529 s | 1.027 s | 1,056 / 1,452 | Exact token match |
| Filesystem LRU after forced RAM eviction | 1.244 s | 0.840 s | 1,056 / 1,452 | Exact token match |
| Filesystem LRU after a fresh engine start | — | 2.042 s | 1,056 / 1,452 | Persistent hit; exact token match |

The forced filesystem run created eight block files totaling 138,412,032
bytes. The fresh-process check opened the existing tier, reported a cache hit
on its first request, and ended with eleven files totaling 190,316,544 bytes.
Windows correctly used buffered I/O because `O_DIRECT` is not available.

### Regression checks

- Focused Windows KV/file-mapping/shared-region/hybrid-block tests: **80
  passed, 1 platform-gated skip, 0 failed**.
- Final-wheel archive, required payload, Windows marker, metadata, CRC, and
  RECORD validation: passed.
- Repository release contracts after the launcher fix: **24 passed, 0
  failed**.
- The RTX 3090 returned to its 6 MiB idle state after every test process.

These are measurements for the listed model and test configuration, not
universal performance guarantees. CPU/filesystem KV offload remains
experimental and disabled by default.
