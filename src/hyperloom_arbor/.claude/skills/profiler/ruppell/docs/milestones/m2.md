## M2.8 on DSV4.1: why outputs cannot decide it, and what does

The served DSV4.1 stack is not reproducible run to run, with or without
tracing: on one untraced server, two passes of the same greedy prompts differ
on 6–8 of 8 prompts (48489, 48796, 48834), and even the prefill alone
differs: first tokens on 3 of 8 prompts, and the prompt's own logprobs by up
to 20 nats, already at the second prompt position, from a cold prefix cache
too (48946). The small model is exactly reproducible. So no comparison of
outputs can bound a tracer effect below the server's own variation; at that
resolution traced-vs-untraced differences are distributed like each server's
own (48946: medians 0.76 and 0.77 nats over 98 positions, one-sided
permutation p = 0.78).

What can be decided exactly is whether tracing changes the GPU program.
Tracing adds step-marker kernels and nothing else on the GPU; hooks run in
Python and the tool only observes. The correctness job runs an untraced
control (the adapter in witness mode: markers only) and the traced server,
both under `rocprofv3`, and compares, per rank, the kernels, order, grid and
workgroup sizes of every step in the first-token phase (prefills of fixed
prompts, whose shapes no generated token or speculative acceptance can
change): `tests/m2/program_check.py` (offline test: `tests/test_program_check.py`).
Result (49062): identical on all 4 ranks, see the M2.8 row.

This replaces the plan's exact-greedy check only where that check is shown
not to be determinate; the operator decides whether it stands for M2.8.

## Found on the way (for the DSV4.1 work, not ruppell)

The served stack's run-to-run variation above: up to 20 nats on prompt
logprobs from a cold cache is far beyond floating-point reordering, which
points at state that differs between runs (vLLM zeroes new KV blocks
precisely because stale data can corrupt attention). Worth a look by whoever
owns the DSV4.1 correctness gate.

**Launch configuration.** The DSV4.1 runs (M2, M3) used the pinned tree
`8f400a0ac` (v2+v6) with the knob-ab screen's base arm: its `vllm serve` flags
and its environment minus the knob flags. That environment is not yet
reconciled with InferenceX's `v2-best-rocm-flags-v6` launch flags (the runner's
decision 0001), so a trace may not match that baseline's configuration
exactly. (Listed among ruppell's limitations until 2026-10-20; it describes
these runs, not the tracer.)

## Found and fixed on the way

- PyTorch reuses graph addresses and exec handles: handles are resolved in
  record order (the first run joined nothing).
- The runner's own work had no scope (0.89 attributed): scopes
  `runner.<method>`.
- vLLM's startup warmup drives `execute_model`; counted as engine steps it
  put a 128-request batch and two stray kernels into the served workload:
  all of `compile_or_warm_up_model` is now warmup steps.
- Served processes are killed rather than finalized (and under `rocprofv3`
  must be): the tool flushes every 5 s, the reader drops a partial record.
- One odd replay refused a whole graph: replays join one by one.
- The profiler SDK sometimes tags a replay's dispatches on a graph's second
  queue with a neighbouring call's correlation id (`hipEventRecordWithFlags`;
  4 kernels once in 17,503 replays): such a replay is completed from the
  dispatch ids it lacks, only when its kernel sequence then matches exactly,
  and the repair is reported.
- Serving under `rocprofv3`: vLLM's Rust frontend outlived a server and held
  the port, and `rocprofv3`'s signal handler looped on an aborting helper
  (20 million log lines): the serve scripts stop `vllm-rs`, wait for the
  port, and bound that log.
- The embedding's 12.7% of GPU time is its all-reduce waiting for the other
  ranks (feasibility-m2).
