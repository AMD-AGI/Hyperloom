Everything ruppell does itself is below this resolution; the cost is the ROCm
profiler SDK's kernel dispatch tracing, about 2 µs of host time per dispatch
inside `hipGraphLaunch` (M2's trace: 3 ms per decode graph launch of about
1,500 kernels), on the step's critical path, and through the rank whose host
lags (docs/analysis/dsv41-c8-tracelens.md). `rocprofv3`'s kernel trace uses
the same mechanism.

## Round b: detail sampling (`771fd94`)

Kernel dispatch tracing now runs in a context of its own, switched per step:
`RUPPELL_DETAIL=5/1000` traces every kernel of 5 of every 1,000 engine steps
(the same steps on every rank; startup, capture and warmup always), while
step fields, CPU step windows, capture callbacks and HIP API records stay on
for every step. Expected cost: about the sampled fraction times 27%, some
0.14% of ITL. A sampled run is validated like a full one; the witness
comparison also checks that every dispatch `rocprofv3` saw inside a sampled
step is in ruppell's records. Small model, 2/10 (job 49440, re-checked by
49515 at `e73ff7b`): 99–108 sampled engine steps, 0 unpaired markers, every
replay joined; inside the sampled steps `rocprofv3` saw 29,733 (TP1) and
55,098 and 52,602 (TP2, per rank) dispatches, **0 missing** from ruppell,
identical times. (A first version of that check counted the next,
unsampled step's begin marker, which starts a few µs before a sampled step's
end marker ends, as missing; it belongs to the next step.)

## The CPU op tree on DSV4.1 (job 49794, `fb7d838`)

`RUPPELL_CPU_OPS=1` (input capture) at full detail, traced against the
markers-only control, both under rocprofv3, C8 first-token and greedy passes.

- **Startup.** The first attempt (49756, `c2c43b0`) killed every worker: the
  callback read the sizes of a `__torch_dispatch__` tensor while
  `make_subclass` was detaching it, PyTorch asserted inside the callback,
  and `on_end` then dereferenced the missing context. Fixed in `fb7d838`;
  49794 served normally.
- **Records.** Witness: every dispatch matched, identical times; registry
  100% on every rank; no dropped records.
- **GPU program (M2.8): fails as written.** Traced 33 first-token steps,
  control 34. The extra control step is empty (markers, no kernels, 83 ms
  into the phase). Ranks 2 and 3 differ by that alone. On ranks 0 and 1
  every step differs in one kernel's grid, the rest identical in order and
  grids: `triton_poi_fused_add_bitwise_and_bitwise_not_bitwise_or_ge_lt_mul_sub_0`
  (an Inductor pointwise kernel), grid 128 (rank 0) and 512 (rank 1) traced,
  256 control. Inductor picks a pointwise kernel's block size by timing
  candidate configurations in each process, so the grid is the choice, and
  the computation is the same. (`program_check.py --explain`, job 49826.)
- **Kernel-time parity: fails as written.** The rank that arrives last at
  the all-reduces moved: in the control rank 3 (its all-reduce time
  shortest), traced rank 1 (its `cross_device_reduce` time 0.17× and 0.05×
  the control's; rank 3's 14× and 23×). Collective time is waiting time, so
  it follows the straggler. Totals per rank 0.99, 0.51, 0.97, 2.17. Non-collective families mostly within 3–5%; rank 3's
  `_inverse_rope_gptj_mx_quant_kernel` reads 1.38× (1.3% share).

**For the operator.** Both failures come from choices the servers make at run
time (Inductor's block size, which rank straggles), not from kernels ruppell
adds or removes. Whether an untraced server makes the same choices twice is
not measured; a control-vs-control pass of both checks would say.
