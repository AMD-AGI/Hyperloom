# v_mfma_f32_16x16x32_bf16

BF16 matrix fused multiply-add, 16x16 output tile, K=32. The primary MFMA for BF16 GEMM and attention on MI355X (XDL2x pipeline). 1.87x throughput over 2x legacy v_mfma_f32_16x16x16_bf16.

---

## Quick Reference

| Field | Value |
|-------|-------|
| Opcode | `v_mfma_f32_16x16x32_bf16` |
| Tile Shape | 16 rows x 16 cols, K=32 |
| Input Type | BF16 (packed pairs in VGPRs) |
| Output Type | FP32 (accumulated in AGPRs) |
| Latency | 16 cycles (4-pass, 2x8) |
| Issue Rate | 8 cycles (can issue new MFMA every 8 cycles to same SIMD) |
| FLOPs | 16 * 16 * 32 * 2 = 16,384 |
| Measured CPI | 15.6 shader cycles (isa-bench, within 2% of spec) |

## Output Layout (Column-Major)

The output is column-major in the AGPR file. Each lane holds 4 AGPRs representing 4 consecutive rows in the same column.

```
Lane L (0..63) has 4 AGPRs: a[k] = C[(L/16)*4 + k, L%16]   for k=0..3

  lane_row = L % 16    -> column index (0..15)
  col_group = L / 16   -> row group (0..3)

  Lane 0:  a[0]=C[0,0]   a[1]=C[1,0]   a[2]=C[2,0]   a[3]=C[3,0]
  Lane 1:  a[0]=C[0,1]   a[1]=C[1,1]   a[2]=C[2,1]   a[3]=C[3,1]
  ...
  Lane 16: a[0]=C[4,0]   a[1]=C[5,0]   a[2]=C[6,0]   a[3]=C[7,0]
  Lane 32: a[0]=C[8,0]   a[1]=C[9,0]   a[2]=C[10,0]  a[3]=C[11,0]
  Lane 48: a[0]=C[12,0]  a[1]=C[13,0]  a[2]=C[14,0]  a[3]=C[15,0]
```

Store path must stride by `ldc` (row stride of output matrix) for consecutive AGPR values. Use `v_accvgpr_read_b32` to move AGPRs to VGPRs before storing.

## Operand Requirements

| Operand | Register | Count | Constraint |
|---------|----------|-------|------------|
| Src0 (A) | VGPRs | 4 | **Must be VGPRs, NOT AGPRs** |
| Src1 (B) | VGPRs | 4 | **Must be VGPRs, NOT AGPRs** |
| Src2/Dst (C/D) | AGPRs | 4 | Accumulator input/output |

Source VGPRs are latched at issue time. A `ds_read` into the same VGPRs on the next cycle is safe -- the MFMA already captured the old values. But the ds_read must complete before the NEXT MFMA that reads those VGPRs.

---

## Co-Execution Window

| Cycle Range | Activity |
|-------------|----------|
| 0-7 | Reads A, B, D operands. **No co-execution.** |
| 8-11 | Free. Co-exec: TEX, LDS, ALU0. |
| 12-15 | Free. Co-exec: TEX, LDS, ALU0, LD_SCALE. |
| 16+ | Can issue next MFMA. |

Back-to-back MFMAs writing to different AGPR destinations can issue at the 8-cycle pipeline rate with zero NOPs between them. Fill the gap with ds_reads and address computation.

## NOP Requirements

| Transition | Required Wait | Consequence if Missed |
|------------|---------------|----------------------|
| `s_waitcnt` -> this MFMA | **0 NOPs** | No hazard (validated across 15+ shapes) |
| VALU write -> this MFMA (same src VGPR) | **2 NOPs** (s_nop 1 x 2) | MFMA reads stale VGPR value (~17-30 instead of 32) |
| This MFMA -> another MFMA (diff AGPR dest) | **0 NOPs** | 8-cycle issue rate is the only constraint |
| Last MFMA -> `v_accvgpr_read_b32` | **64 NOPs** (s_nop 15 x 4) | Non-deterministic NaN, values in thousands |
| `v_accvgpr_write_b32` -> this MFMA (same AGPR) | **1 NOP** (s_nop 0) | MFMA accumulates into stale value |

### MFMA Drain Disagreement

There is a documented contradiction in the empirical data on MFMA-to-ACCVGPR_READ drain:

- **Initial testing**: Validated 1x s_nop 15 (16 cycles) as sufficient in some contexts.
- **Later testing**: Found 2x s_nop 15 (32 cycles) INSUFFICIENT in the same opcode, causing non-deterministic NaN at deep layers (L6-L20 in decode).
- **Conservative rule**: Use 4x s_nop 15 (64 cycles) unless you have validated your specific use case empirically on real hardware.

The FWD attention swarm also found NOPs required even with 192+ intervening instruction cycles, suggesting the pipeline drain is longer than the cycle count implies.

## Known Bugs / Gotchas

1. **accum_offset must include AGPRs in next_free_vgpr**: `.amdhsa_next_free_vgpr = accum_offset + num_agprs`. If `next_free_vgpr == accum_offset`, zero AGPRs are allocated and MFMA writes vanish silently. The #1 gfx950 assembly bug.

2. **AGPR aliasing**: VGPRs at index >= `accum_offset` physically alias AGPRs. A `ds_read_b128` to v[accum_offset+N] silently clobbers accumulator a[N]. All compute VGPRs must be below `accum_offset`.

3. **Output is column-major, not row-major**: Every agent that writes GEMM/attention kernels rediscovers this. Swapping row/col in store path produces transposed output.

4. **Compiler-inserted inter-MFMA NOPs are unnecessary**: The hardware handles inter-MFMA hazards internally on gfx950. Confirmed by 5+ agents independently.

5. **v_cvt_pk_bf16_f32 required for BF16 packing**: Manual `v_lshrrev_b32 >> 16` to extract BF16 from FP32 produces inf/NaN on gfx950.

## Use Cases

- **BF16 GEMM (128x128 tile)**: 16 MFMA blocks per output tile, 64 AGPRs total. 4 waves per WG, occupancy=4 waves/SIMD with 124 VGPRs.
- **BF16 attention (FWD/BWD)**: Primary compute instruction in attention kernels. BWD uses ~480 MFMAs across 5-GEMM decomposition.
- **DeepSeek-V4-Flash inference**: Used in all BF16 GEMM stages of the inference pipeline.
- **Software pipelining**: Issue global loads during co-execution window (cycles 8-15) to hide HBM latency (~200-400 cycles).

## Register Allocation Example (128x128 BF16 GEMM)

```
v[0:13]     Thread identity, wave decomposition, LDS write bases
v[14:21]    LDS read addresses (persistent across K-loop)
v[28:31]    MFMA B operand buffer (alternate)
v[40:43]    MFMA A operand buffer
v[44:47]    MFMA B operand buffer (primary)
v[48:55]    Global load destination buffers
a[0:63]     MFMA accumulators (16 blocks x 4 AGPRs)

accum_offset = 60
next_free_vgpr = 124  (= 60 + 64)
```
