PHASE 1 · GETTING IT RUNNING

Three Patches to Boot the Model

3 patches
Prerequisites before any benchmarking

Qwen3.5-397B uses a hybrid linear/full attention architecture (gated delta net) that exposed three incompatibilities in the AMD SGLang stack. Without these patches, the server crashes on startup.

patch 001 CuteDSL KDA AMD compat — Linear attention layers import CUDA-only JIT code unconditionally. Guarded behind is_cuda() to prevent crash on ROCm.
patch 002 Disable multimodal pipeline — SGLang flags Qwen3.5 arch names as potentially multimodal, triggering init that fails on this text-only model. Added to mm_disabled_models list.
patch 003 Empty tensor guard — During CUDA graph capture, hybrid attention layers receive empty tensors for inactive attention types. Added early-return guards in Qwen3_5GatedDeltaNet and decoder layers.

PHASE 3 · WINNER

tuning_v2 — Decode Batching + Mixed Chunk

313.69 tok/s/GPU
+4.7% from baseline · +25.2% vs reference at CONC=64

The winning configuration: 8 continuous decode steps, mixed-chunk scheduling, and mem-fraction 0.85. Consistent +3.3–4.7% gain across all concurrency levels. Chunked prefill at 32K tokens.

decode-steps 8 Batches 8 decode iterations before rescheduling, reducing scheduler overhead per token
mixed-chunk Mixes prefill and decode tokens in same batch, eliminates GPU idle time between phases
mem-fraction 0.85 5% more GPU memory for KV cache (vs default 0.80), allows more concurrent sequences before eviction
chunked-prefill 32768 Controls prefill granularity to balance prefill latency with decode throughput

EXPERIMENT · FP8 KV CACHE

tuning_v3 — FP8 KV + Decode Steps 16

Worse than v2
Regression · Quantization overhead > memory savings

Enabling FP8 KV cache on a BF16-weight model added quantize/dequantize overhead on every attention operation that exceeded the benefit of fitting more sequences in memory.

FP8 KV The quant/dequant cycle runs on every attention op across all layers. For BF16 models this is net negative — FP8 models may benefit differently.
decode-steps 16 Doubling from 8 to 16 decode steps did not help — 8 is already near the sweet spot for scheduling amortization.

EXPERIMENT · EXPERT PARALLELISM

EP-8 — Expert Parallelism

-2% to -6%
Regression · Routing overhead at TP=8

At TP=8, all experts are already on all GPUs. Expert parallelism added all-to-all communication overhead for routing without reducing per-GPU compute. Net negative.

all-to-all Expert routing requires all-to-all communication between all 8 GPUs. The overhead exceeds compute savings when experts aren't actually distributed.

EXPERIMENT · MIXED PARALLELISM

TP-4 DP-2

Better TTFT, worse throughput
Regression at high CONC · Half KV cache per replica

Two replicas with 4 GPUs each improved prefill latency (TTFT) but degraded throughput at high concurrency. With only 4 GPUs per replica, KV cache capacity halves, causing earlier eviction under load.

KV capacity At CONC=64, each replica serves 32 concurrent — half the available KV cache causes eviction pressure that dominates the throughput picture.
TTFT win Prefill latency improved since each replica handles fewer concurrent prefills. Good for latency-sensitive workloads at low concurrency.

EXPERIMENT · ATTENTION BACKENDS

aiter / alter Backends — Server Crash

CRASH
Incompatible with hybrid linear/full attention

Both aiter and alter attention backends crashed on Qwen3.5's gated delta net layers. These backends expect standard MHA/GQA/MQA patterns. Only triton works for this architecture. This eliminates the biggest optimization lever seen on GLM-5 (+21%).

aiter Crashes on gated delta net layers — expects standard attention patterns, not hybrid linear/full.
alter Same crash. Full attention every 4th layer is insufficient coverage for alter to help even if partial routing worked.
impact This is the primary reason for the ~49% gap vs B200 at low concurrency. B200's trtllm_mha handles hybrid attention natively.

Key insight: The hybrid linear/full attention architecture is the dominant constraint. It forces the generic triton backend (aiter/alter crash), which is the primary cause of the ~49% gap vs B200 at low concurrency. At high concurrency (CONC≥32), batch size amortizes per-token kernel overhead, and MI355X's comparable HBM bandwidth (~8 TB/s both) plus scheduling optimizations close and exceed the gap. The low-concurrency gap is closeable with software once an optimized backend supports hybrid attention.
