③ ⭐ 内核优化是怎么拿到的 — 五步全过程

这是本次会话的核心产出。从 trace 定位到 E2E 落地,全链路 Aug11 17:43 → Aug12 02:29(约 8h45m),其中 KernelForge 搜索仅占 55 分钟。

STEP 4 展开 · 内核改写手法(节选真实 diff)

① 把 cache 内层 stride 声明为 constexpr —— 修复访存合并
最有"含金量"的一处:Triton 的 AxisInfo 无法证明 stride*offset 的连续性,AMD 后端于是把整块 cache tile 退化成逐元素 buffer_load_ushort。ISA dump 实测:每个 context tile 63 条 2 字节标量加载,对 64 条 MFMA。声明为编译期常量后,分析可看到 8 元素(K,沿 head-dim)/ PHYSICAL_BLOCK_SIZE 元素(V,沿 token)的连续段并加宽访存。值没变,只是把本来就固定的 stride 特化给 JIT。
-    stride_k_cache_x,
+    stride_k_cache_x: tl.constexpr,
-    stride_v_cache_bl,
+    stride_v_cache_bl: tl.constexpr,
② base-2 softmax + 缩放下沉到行最大值
qk 预乘 log2(e) 后用 tl.exp2,可发原生 v_exp_f32 而不是 libm 的 expf 多项式。同时 不再缩放 [BLOCK_M, BLOCK_SIZE] 的整块分数(每元素多一条 VALU 且正好压在两次 MFMA 之间的关键路径上),而是把正缩放因子作用在已归约的 [BLOCK_M] 行最大值上,折进指数里收缩成一条 v_fma_f32。
-    qk = sm_scale * tl.dot(q, k, ...)
+    qk = tl.dot(q, k, ...)
+    qk_scale = sm_scale * RCP_LN2
-    m_ij = tl.maximum(m_i, tl.max(qk, axis=1))
-    p = tl.exp(qk - m_ij[:, None])
-    p = tl.where(m_ij[:,None]==-inf, 0.0, p)
+    m_ij = tl.maximum(m_i, tl.max(qk,axis=1)*qk_scale)
+    p = tl.exp2(qk * qk_scale - m_ij[:, None])
# max(s·x)==s·max(x) for s>0,-inf·s 仍是 -inf
③ 分页 context 循环软流水化
原循环在每次 tl.dot 前串行两次相互依赖的全局加载:block-table 查表产出物理页号,K/V 地址才能算。num_stages=1 下编译器无法跨迭代提升这条依赖链。只把链头旋转一个迭代:本 tile 用已就绪的页号立即发 K/V,同时把下一 tile 的查表放飞。预取索引被钳到最后一个有效 tile/token,免谓词且不越界。
+    bn = bn_pf          # 上一轮预取好的页号
+    bn_pf = tl.load(B_Loc + ... +
+        tl.minimum(tl.minimum(start_n+BLOCK_SIZE,
+            ctx_last_start)+offs_bs_n, ctx_last_tok)
+        // PHYSICAL_BLOCK_SIZE * stride_b_loc_s)
④ 对角线下免掩码快路 NO_MASK_OK
因果块中严格位于对角带之下的 key tile 全部有效:既不需要 load 掩码,也不需要注意力掩码、−inf select 和全掩码行保护。长 prefill 下这是绝大多数 tile,走通用带掩码主体等于每个 tile 白扔一次谓词加载加三次 [BLOCK_M, BLOCK_N] 的 select。快路里还把 V 与 K 并发发出,让 V 取数重叠 q@k 的 MFMA 与整条 softmax 链。
+ NO_MASK_OK: tl.constexpr = (CAUSAL
+   and SLIDING_WINDOW <= 0
+   and BLOCK_DMODEL == BLOCK_DMODEL_PADDED
+   and BLOCK_M % BLOCK_N == 0)
+ if NO_MASK_OK:
+   for start_n in tl.range(0, diag_start, BLOCK_N,
+       loop_unroll_factor=..., num_stages=2):
+     k = tl.load(...); v = tl.load(...)  # 无谓词
⑤ 最长作业优先(LPT)派发
每个 program 的工作量随 start_m 线性增长 —— 因果自注意力循环在固定 context 循环之上多跑 start_m 个 tile,最后一个 M 块的工作量约为第一个的 2 倍。而块是按线性 id 升序交给 CU 的、M 是最慢变分量,于是默认顺序把最便宜的块排在最前,尾部清一色是最贵的块。反转索引让重块先跑、轻块填尾。纯索引重命名,每个 (batch, head, m) 三元组仍恰好执行一次。
-    start_m = tl.program_id(2)
+    start_m = tl.num_programs(2) - 1 - tl.program_id(2)
⑥ 删掉已成死代码的保护 select
该循环的 tile 必然含至少一个范围内的 context key(循环边界保证 start_n < cur_batch_ctx_len),且越界 query 行读到的 q 为 0,故 m_ij 永不为 −inf。通用路径需要的两个保护 select(全掩码行的 p==0 / alpha==0)在此已是死代码 —— exp2(-inf - finite) 本就精确得 0。删掉它们等于每迭代省下两个完整的 [BLOCK_M, BLOCK_SIZE] select。
-    alpha = tl.exp(m_i - m_ij)
-    alpha = tl.where(m_i == -inf, 0.0, alpha)
+    alpha = tl.exp2(m_i - m_ij)
另有 TRITON_BLOCK_SIZE 32 → 64(in-session gate 记录 edit=32 ALLOW 1.1815x)。补丁最终形态取自 forge_experiments/best/iter_003/forge.patch,经 _deploy.patch 落到 /usr/local/lib/python3.12/dist-packages/vllm/...,并在 patches/k001/backup/ 留有可回滚快照。

关键观察
  • ISL=8K 的长 prefill 让 attention 成为压倒性瓶颈:单核占 24.41% GPU 时间而效率仅 6.96%,是全部 15 个候选里唯一"占比高 + 效率低 + 源码可改"三者同时成立的,因此内核阶段的靶心毫无悬念。
  • 内核收益来自编译器/调度层面的洞察,而非算法替换:五类手法里最关键的两个 —— stride 特化修复访存合并(ISA 里 63 条 2 字节标量加载 vs 64 条 MFMA)、LPT 反转派发压紧尾部 —— 都是"读懂后端行为"的产物,单看 Triton 源码是看不出来的。
