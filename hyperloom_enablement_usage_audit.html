④ 结论

  • enablement 的参与面确实很大:42/151 = 27.8% 的会话都动用了它,累计 155 次 enablement_specialist 运行。而它是全部域中单次最贵($12.62)、轮次最多(103.5)、提案最少(1.8/次)、空手率最高(28.4%)、每提案最贵($6.96)的一个。
  • 它的触发是系统性的,不是偶发的。六个模型族 100% 触发,而 Qwen3-0.6B / Qwen3-8B 等共 60+ 个会话一次都没触发。这说明问题在特定模型的镜像与默认配置,不在运行时抖动 —— 也就是可以从源头修掉的。
  • 同一个失败在被反复付费诊断。28 个会话落入 9 个"同模型同签名"重复组,合计 $3,609 账本花费、其中 $1,560 花在 121 次 enablement 运行上。DeepSeek-V4-Pro-MXFP4 在同一天内把同一个 EngineCore failed to start 诊断了 7 遍,7 次全部零增益。
  • 修复动作是明确的:把已诊断出的启动修复回流到镜像/默认配置,并为已知失败签名建立跨会话的持久台账 —— 让第 2 次遇到同一签名时直接套用已知修复,而不是重新派发一个 100+ 轮的 specialist。按重复组的口径,这一项的直接可回收金额约 $1,560,连带解锁被 baseline_tput <= 0 阻塞的全部下游优化产出。
一个诚实的边界:数据集只覆盖 2026-08-11 与 08-12 两天,所以"跨天复现"只在 GLM-5.2-MXFP4 与 MiniMax-M3-MXFP4 上直接观测到;DeepSeek-V4-Pro-MXFP4 的 7 次相同失败发生在同一天内。要论证真正的"逐日"重复需要更长时间窗 —— 但同日 7 次重复同一诊断,已足以说明问题不在会话侧。另外失败签名的归一化是我自定义的启发式(抹数字/路径后提取错误关键字),对签名边界敏感;重复组数量在该方法下是下界。
数据来源:sessions.csv 全 159 行对应归档的 session_breakdown.json(enablement.* / specialist_runs[].domain / session.stop_reason / capability_summary.specialist)、storage/coordinator.db 的 tasks 表(idempotency_key / params)、reports/trace/llm_calls.jsonl(按 task_id 归因 enablement 花费),以及 session-money.csv 的账本口径花费。代码侧参照 orchestrator/loop/coordinator.py(_ENABLEMENT_MAX_STALL = 5)、orchestrator/phases/framework.py(enablement 轮次的 rearm / stall 记账)、orchestrator/loop/dispatcher.py(baseline_tput <= 0 时以 rule="execution_order" 硬拒 explore)。
