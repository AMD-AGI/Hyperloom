# Knowledge-Base Guide

> **Scope.** This page explains the two knowledge-base (KB) stores
> referenced by Hyperloom, how to obtain or populate them, and what to
> do when you don't have either. Both KB stores are **optional** for a
> first run; Hyperloom degrades gracefully when they are missing.

Hyperloom references two distinct KB stores:

| KB                                     | Owner / process                | Purpose                                                                                              |
|----------------------------------------|--------------------------------|------------------------------------------------------------------------------------------------------|
| **`INFERENCE_OPTIMIZER_KB_ROOT`**      | `inference_optimizer` / Critic | Cross-run optimization lessons (architecture quirks, validated wins, crash patterns).                |
| **Marathon KB** (`marathon_optimization/kb/`) | Marathon offline pipeline      | Bulk-import store of per-model optimization traces used to seed `INFERENCE_OPTIMIZER_KB_ROOT`.        |

The two stores share a JSONL schema (`{category, model, lesson, confidence, ...}`)
but are populated by different pipelines.

---

## 1. TL;DR — I just want to start a run

You don't need either KB to start. Run optimization without setting
`INFERENCE_OPTIMIZER_KB_ROOT`, and Hyperloom will:

* Skip the KB-prior step in scoring (every action starts at its base
  prior, no boosts and no penalties).
* Skip the post-action `kb_ingest` step (no new lessons are written).
* Continue normally through baseline, roofline/profile, explore, kernel
  optimization, sweep, and report.

Expect modestly worse performance on the **first** run (the agent may
re-discover known dead ends), but correctness is unaffected.

To suppress the "KB not configured" warning during a run, set
`INFERENCE_OPTIMIZER_KB_ROOT=skip`. The CLI treats any non-existent
path as "KB disabled".

## 2. `INFERENCE_OPTIMIZER_KB_ROOT` — cross-run optimization KB

### What it is

A directory of JSONL files, one per category, containing validated
lessons accumulated across optimization runs. Each entry looks like:

```json
{
  "id": "lesson-2026-04-glm5-001",
  "category": "lesson",
  "model_class": "moe_mla_nsa",
  "model": "GLM-5-FP8",
  "action": "explore",
  "lesson": "Super-linear synergy: combining --nsa-decode-backend aiter, --enable-mixed-chunk, and --enable-aiter-allreduce-fusion gave +41.2% combined vs +3%/+3%/+0.3% individually.",
  "confidence": 0.92,
  "evidence_paths": ["sessions/glm5-20260415/state.json"],
  "superseded_by": null,
  "importance": 0.84
}
```

The Critic agent owns reads and writes; the Coordinator and specialist
warmup paths surface relevant priors during the live optimization loop
(see [HOW_THE_OPTIMIZATION_LOOP_WORKS.md](HOW_THE_OPTIMIZATION_LOOP_WORKS.md)).

### Layout

```
$INFERENCE_OPTIMIZER_KB_ROOT/
├── lessons.jsonl          # validated cross-run lessons (most important)
├── pitfalls.jsonl         # known crash / regression patterns
├── architecture.jsonl     # per-model-class architecture facts
├── benchmarks.jsonl       # validated benchmark methodology notes
└── index.json             # generated; do not edit
```

`index.json` is regenerated by Critic on every write; you only need to
ship the `.jsonl` files.

### How to obtain it

Three options, in order of preference:

**Option A — Use the seed KB shipped with a Hyperloom release.**
Once Hyperloom publishes a tagged release with bundled KB, download
the `kb-vN.tar.gz` asset and extract:

```bash
mkdir -p "$HOME/.hyperloom/kb"
tar -xzf kb-v1.tar.gz -C "$HOME/.hyperloom/kb"
export INFERENCE_OPTIMIZER_KB_ROOT="$HOME/.hyperloom/kb"
```

> **Status (as of v0.6.0).** A public seed KB is **not yet shipped**.
> See [the open issue](https://github.com/AMD-AGI/Hyperloom/issues) for
> tracking.

**Option B — Populate it yourself from your own past runs.**
After completing a few optimization sessions, run:

```bash
python -m inference_optimizer.scripts.dump_session_breakdown \
    --session-dir "$USER_DATA_PATH" \
    --output /tmp/breakdown.json
# Use the breakdown as input to critic-agent's KB draft action.
```

The Critic agent's `actions/draft_kb.md` describes the lesson-extraction
flow; the resulting `.jsonl` entries can be appended to your local KB
root.

**Option C — Skip it.**
Leave `INFERENCE_OPTIMIZER_KB_ROOT` unset (or `=skip`). Hyperloom runs
fine without it, just with cold-start scoring priors.

### Where to put it

The path is arbitrary, but recommended layouts:

| Setup                       | Suggested path                                    |
|-----------------------------|---------------------------------------------------|
| Single-user laptop / pod    | `$HOME/.hyperloom/kb`                             |
| Shared WekaFS mount         | `/wekafs/hyperloom/kb`                            |
| Hosted PrimusClaw sandbox   | Pre-mounted; do not override.                     |

## 3. Marathon KB — offline bulk import

The `marathon_optimization/` subtree is an **offline** pipeline that
batch-processes session breakdowns from many models into a single KB
suitable for seeding `INFERENCE_OPTIMIZER_KB_ROOT`. It is **internal
tooling** and not required for normal Hyperloom use.

If you are not running the marathon pipeline, you can safely:

* Ignore the `marathon_optimization/` directory.
* Leave any `MARATHON_KB_*` environment variables unset.

If you are running it (typically AMD-internal users with access to
historical session archives on WekaFS), see
`marathon_optimization/README.md` in the marathon subtree for the
pipeline-specific instructions.

## 4. KB-unreachable behaviour

When `judge_bundle.kb_read_skipped_reason == "kb_unreachable"` (or
`kb_read_disabled`), Critic was unable to read the KB for that turn.
The runtime treats this as **unknown**, not as *no contradicting
prior*:

* `approve` verdicts become rarer; Critic prefers `advise` or
  `needs_review` based on packet evidence alone.
* The verdict `notes` field carries the missing-KB reason for downstream
  observability.
* Optimization continues; only confidence is degraded.

KB write failures are non-fatal — they log a warning, retain the draft
in `$USER_DATA_PATH/critic-session-memory/kb_drafts/`, and proceed.

## 5. Quick FAQ

**Q: I'm on PrimusClaw. Do I need to set anything?**
No. The sandbox mounts a shared KB and sets
`INFERENCE_OPTIMIZER_KB_ROOT` for you.

**Q: My first run will be slower without the KB. By how much?**
Anecdotally, 10–30% slower wall-clock to a comparable result on
already-explored model classes, because the agent re-discovers known
crash patterns instead of pruning them up-front. New / unstudied
model classes are unaffected (KB has no priors there either).

**Q: Will Critic refuse to approve anything if the KB is down?**
No. Critic falls back to **packet-only evidence**: if before/after
benchmark + accuracy gate + rollback are all in the packet, it can
still approve. It just won't cite cross-run priors.

**Q: Can I use a read-only KB?**
Yes. Mount the directory read-only; KB writes will log
`kb_unreachable` warnings and continue. Reads still work.

**Q: How big is a populated KB?**
A single-model KB is typically <100 KB; a full cross-model KB
(7+ models, hundreds of entries) is ~1 MB. Storage is not a concern.
