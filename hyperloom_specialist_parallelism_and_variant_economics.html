三个主旨

主旨 ①
specialist 消耗的 token 是合理的
花费随调查深度(轮次)增长,与提案数负相关(r = −0.168 vs +0.259)。主流域每提案 $0.88–$2.29,单次运行中位 $4–8 换来 40–100 轮源码/PR/主机探查 —— 这个单价对深度调研是合理的。缓存已把这部分开销压掉 82%。
→ "多召回变体导致 token 浪费"的推断不成立:多提案的运行反而更便宜。
主旨 ②
变体召回太多,排队却进不了测试
4,377 个提案里最多 758 个上过 GPU。每轮 grid 中位只测 4 个,而轮次开始时已有 27 个提案在等。316 个 grid 轮次中没有一轮清空过积压,队列从 18 单调涨到 50。
→ 瓶颈是产出端可并发、消费端单通道串行,不是哪一轮漏掉了谁。
主旨 ③
变体成本总体可控,但 enablement 是失控点
主流域每个提案 $0.88–$2.29,可控。但 enablement_specialist 单次 $12.62、103.5 轮、空手率 28.4%、每提案 $6.96 —— 它在每天的 CI 里反复兜底把模型拉起来,而不是配置本身就能启动。
→ 每天花同样的钱做同一件事,这是最该修的地方。

① 的结论
  • specialist 并不是串行的,108 个会话里 79 个峰值并发为 2、10 个为 3。此前基于「完成时刻间隔稀疏」的串行判断是错的 —— 中位时长 6.5–8.6 分钟的两个错开任务,完成时刻本来就会隔很远,该指标无法区分交错并发与逐个串行。
  • 但真实并发度只有 1.13,而上限最高开到 16。缺口的两个来源性质完全不同:tp=1 会话(60/108)cap=2 是真瓶颈,57/60 触顶、12.2% 的时间被钉在上限;tp=8 会话则是 gpu_research_lane=1 的物理约束,与 cap 无关。
  • 因此「cap 无用可以删掉」是危险的。它恰好是 tp=1 这批会话(机队主体)的当前瓶颈;若删掉启动时的同步而让容量回落到 DEFAULT_LANE_CAPACITIES 的 1,现在能跑 2 的会话会变成完全串行,与目标相反。正确动作是抬高,并改掉 87.7% 单发的派发方式。

② 变体召回过剩 — 队列只进不出

② 的结论
  • 召回与消费的吞吐比是结构性的。产出端 specialist 可并发(cap 2–16),消费端 benchmark_lane 恒为 1、变体串行测试、每变体实测中位 13 分钟、超时下限 40 分钟。EXPLORE 阶段中位 3.5 小时,吞吐上限约 4.6 个变体/小时 —— 一轮放 27 个也确实跑不完。
  • 最终转化链:4,377 个提案 → 3,532 个去重 → 1,487 个变体上机(其中 758 个 specialist 出身)→ 123 个 KEEP。提案到采纳的端到端转化率 2.9%,每个 KEEP 摊 $97.39。被测变体的结局是 REVERT 72.4%、FAILED 13.1%、KEEP 8.3%、KEEP_UNSTABLE 6.1%。
  • 三层缺失的去重会让 GPU 时间白烧。已测指纹可被静默重跑、已采纳配置会被重测出接近零的增益,而这两种情况在串行单通道上每次都要付 13–40 分钟。在积压 6.6:1 的情况下,把 GPU 时间花在重复项上的代价被放大了。

③ 成本结构 — 花费随调查深度增长,单位成本总体可控

specialist 的开销几乎全部来自多轮 agentic 探索所累积的上下文。这笔上下文开销本身就是为了产出变体而付的,不能与"产出"切开来记账 —— 探索与提案是同一件事的两面。因此下面不去区分"上下文 vs 产出",而是直接看:成本由什么驱动、单位成本是否合理。
驱动因子 · 轮次
轮次越深,每轮越贵
每轮的 input+cache_read 从第 1 轮的 2.75 万 涨到第 60 轮的 10.13 万(3.7 倍),中位 59 轮累计 86.99 亿 token。每轮的工具结果都会留在上下文里被后续轮次反复重读。
成本 ∝ 调查深度。要动成本大头,只能减少轮次或压缩注入体积。
非驱动因子 · 提案数
提案多的运行反而更便宜
每次运行花费与提案数的相关系数 −0.168(负),与轮次数才是 +0.259。产出 6 个提案的运行中位花费 $4.46,产出 0 个的是 $5.86。
召回更多变体不会推高成本 —— 提案数不是成本驱动因子。
已有优化 · 缓存
prompt 缓存已省下 82%
这 86.99 亿 token 若全按 input 单价要 $43,400,实际支出 $7,808。缓存出现在 99.9% 的轮次上,每次运行中位写入 43.4 万 cache token。
上下文开销确实高,但已经被优化过一轮了,剩余空间在缓存写入频次上。
单位成本 · 主流域
每提案 $0.88 – $2.29
对于要读框架源码、查 GitHub PR、在主机上跑探测的深度调研,单次 $4–8 换 40–100 轮工作,这个单价是合理的。research_scout $0.95、system $0.88 是全域最优。
→ 结论:specialist 的 token 消耗整体合理,失控只出现在单一个域(见下)。

③ 的结论 · 真实的浪费在哪
  • 主流域的单位成本是可控的。research_scout $0.95/提案、system $0.88、static_recon $1.15、serving $1.91 —— 对于要读源码、查 PR、跑主机探测的深度调研,这个价格是合理的。八个域里有七个落在 $0.88–$2.29 这个窄区间内。
  • 唯一的离群点是 enablement:$6.96/提案,是次高者(freeform $2.29)的 3.0 倍、最优者(system $0.88)的 7.9 倍。它的成因不是单价贵,而是用最多的轮次(103.5)换来了最少的提案(1.8/次),并且有 28.4% 的运行连一个提案都没产出 —— 详见 ④。
  • 空手运行:$2,089,占 specialist 支出的 20.6%。170 次运行返回 empty: true,中位 46 轮(非空是 52 轮)—— 它们做了几乎同等的工作量,产出为零。这是定义最清晰、最无争议的浪费。
  • 同 gap 被多域重复探索:$2,660,占 26.2%。676 个 gap 里有 58 个被 2–5 个不同域各自探索过。这部分不能全算浪费(不同域确实是不同视角),但那 309 个跨域重复的提案说明至少一部分是真的在重做同一件事 —— 这是浪费的上界而非确值。
  • 自动重试占比很小:1,626 个 specialist 任务里只有 44 个带 _auto_retry_attempt(2.7%)。

④ ⭐ 最该修的地方 — enablement 每天在为同一件事付费

enablement_specialist 的任务不是优化性能,而是让模型先能启动。它是各项指标里唯一全面异常的域:单次最贵($12.62)、轮次最多(103.5)、提案最少(1.8/次)、空手率最高(28.4%)、每提案最贵($6.96)。

提案内容证实它在做「兜底」而不是「优化」

抽样这 20 个会话的提案原文,全部是正确性/启动修复,与性能无关:
提案名理由(原文摘要)
force-supported-sparse-mla-mqa绕开 ROCm 上未实现的 sparse forward_mha 路径,走已暴露的正确性回退
mxfp4-aiter-w4a16-correctness强制 AITER W4A16 而非自动选中的 W4A4,针对重复 token 的数值崩溃
disable-expert-parallel-routing256 专家跨 8 rank 分片是 hidden state 全局损坏的嫌疑源,改用张量并行 MoE
eager-execution-numerics用 eager 执行隔离 CUDA graph 缓冲区陈旧或形状特化失效的问题
为什么这是「不健康」的
  • 这笔钱每天都在重复付。enablement 的工作性质是把「当前镜像/配置下模型跑不起来」这个问题现场诊断出来并打补丁。但只要上游的镜像与配置没有真正修好,第二天的 CI 会遇到完全相同的启动失败,再花一遍同样的钱做同样的诊断。这与优化类 specialist 不同 —— 后者的产出会沉淀进 KB(warm_start_recipe / lessons / pitfalls)并在后续会话中复用,而启动修复若不回流到镜像或默认配置,就没有任何积累。
  • 它的成本结构也最差。103.5 轮/次是全域最高(是 research_scout 的 2.7 倍),意味着上下文累积最严重;而按 ③ 的模型,成本随轮次增长,所以它天然落在最贵的一端。同时 28.4% 的空手率说明近三成的这类高成本运行连一个提案都没产出。
  • 它还阻塞了全部下游价值。因为 baseline_tput <= 0 会硬性拒绝 explore,一次 enablement 失败等于整个会话的优化产出归零。20 个会话 $1,768、零增益,就是这个机制的直接后果。

⑥ 方法与数据来源

关键测量方法
  • 并发度:storage/coordinator.db → tasks.history 的 queued→running→succeeded 时间戳重建运行窗,扫描线法求峰值与时间加权均值。这是一手记录,不是从完成时刻间隔推断的。
  • 成本归因:reports/trace/llm_calls.jsonl 的 task_id ⨝ session_breakdown.json 的 specialist_runs.task_id,取 domain / proposals_total / empty。费率按 opus 系列价目表(input $5/M、output $25/M、cache write $6.25/M、cache read $0.5/M),与 Pulse 侧口径一致。
  • 变体计数:capability_summary.explore.tested,并用 len(explore_search.tested) 交叉验证(101 个会话零处不符)。
  • 积压:提案以其产出 specialist 的 completed_at 定时,与各轮 grid 的首个变体时间戳比较,按名字匹配扣除已消耗项。
已知的数据质量限制
  • 17 个会话追踪粒度不同:它们把每次 specialist 的整个生命周期压成一行 ledger(calls_specialist 中位 13,正常会话是 1,162)。所有按调用次数或按轮次的统计(包括每轮上下文规模)都排除了它们。
  • 上下文开销无法与"产出变体"分开记账:多轮探索正是为了产出提案而进行的,所以本报告不主张"提案本身很便宜";关于成本的判断只建立在单位成本(每提案 $)与驱动因子(轮次 vs 提案数)两个口径上。
  • 提案转化率是区间而非点值:按 provenance 算 758/4,057 = 18.7%,按提案名精确匹配算 9.1%,差异来自 LLM 组 grid 时改名或合并。真实值在两者之间。
  • 100% 转化并非目标:提案集里故意包含互斥备选(见到过原文写「仅在 patch 001 无法应用时使用」),所以缺口不能全部解读为损失。
  • 33 个归档没有 coordinator.db,均为早期失败会话 —— 并发测量对"跑起来了的会话"无偏,但对全体会话有生存偏差。
  • 24 个会话因金额口径不符被排除在成本统计外(SBD 的 money 漏记了大部分 specialist 用量),但并发测量不受此影响,故仍纳入。
